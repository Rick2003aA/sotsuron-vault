# 技術的負債（Technical Debt）— 定量化の試みと「誇張」される数字

メモ作成：2026-11-21 Muse（各数値は検索で出典を確認。引用前に原典確認）

## 起源
- Ward Cunningham (1992) "The WyCash Portfolio Management System"：短期的に手早く書いたコードは「借金」で、元本（作り直しコスト）と利子（その後の変更のたびに払う余分な手間）が発生する、という金融メタファー。本来は経営層への説明のための比喩で、測定概念ではなかった。

## 「問題視・誇張」の代表例（いずれも出し手に立場がある）

### 1. Stripe『The Developer Coefficient』(2018) — 最も有名な誇張例
- 開発者は週41.1時間のうち17.3時間（約42%）を保守・技術的負債対応に使っている（うち技術的負債13.5時間、bad code 3.8時間）
- bad code の機会損失は年850億ドル、開発者の非効率全体では年3,000億ドル、今後10年で世界のGDPを3兆ドル押し上げ得る、と試算
- 実態：Harris Poll による自己申告アンケート（開発者1,000人超＋経営層1,000人超、6か国）から、開発者数×GDP換算でトップダウンに膨らませた推計。Stripeは決済＝開発者向けサービスの会社。

### 2. CISQ『The Cost of Poor Software Quality in the US』(2022)
- 米国の技術的負債の蓄積額を約1.52兆ドル、ソフトウェア品質の悪さの総コストを年2.41兆ドルと推計。トップダウン推計で「桁感」の数字。

### 3. CAST Research CRASH Report (2011/12)
- 745アプリ・3.65億行を静的解析し「技術的負債はコード1行あたり平均3.61ドル」。100万行のシステムなら負債361万ドル、という換算が一人歩きした。
- 実態：解析ツールベンダー（CAST）のルール違反カウントを金額換算したもの。アーキテクチャ上の負債や業務ルールのブラックボックス化など、最も高くつく部分は静的解析では測れない。

### 4. McKinsey (2021)
- CIOへの調査で「技術的負債はIT資産価値の20〜40%に相当」。自己申告ベース。

### 5. 日本版の誇張：経産省『DXレポート』(2018)「2025年の崖」
- レガシーが残存すれば2025年以降「年間最大12兆円（現在の約3倍）」の経済損失、という試算。条件付きの最大値で、内訳・発生確率は分解されていない。
- 2025年を過ぎた現在、モダン化委員会総括レポート(2025)は「進捗は依然スピード感に欠ける」と総括したが、崖のような断絶的イベントは起きていない。警告の数字と実績の乖離を事後的に検証できる、日本の卒論ならではの論点。

## 卒論での扱い方
- 技術的負債の「金額」は、測定ではなくレトリック（危機を煽って投資を正当化する装置）として分析対象にできる。誰が・何を売るために出している数字か（決済会社、解析ツールベンダー、コンサル、経産省）を見ること。
- 学術的には Kruchten et al. (2012) "Technical debt: From metaphor to theory and practice" (IEEE Software) が比喩から概念への整理として引用可能。
- 本研究の対象は負債の金額ではなく、負債が「なぜ返済されず再生産されるか」の構造なので、これらの数字は第2章で「問題の大きさが語られる言説」として紹介し、額面通りには採用しないのが安全。
